# M3: `GivensQ`, the implicit Q representation — Implementation Plan

**Milestone closed by a failed gate.** Task 2's gate measured `GivensQ` against `DenseQ` over an
active-set working-set loop on two machines (`galen`, then this development machine); both agree
`GivensQ` is 3x-13x slower than `DenseQ` at every shape and turnover measured, and every `k = n`
row falls far short of the required `ratio >= 1.10`. `GivensQ` is not built. The `AbstractQRep`
seam stays: the gate ruled out this one alternative representation, not every possible one —
compact WY was never measured — and the seam costs little to keep. See
`.superpowers/sdd/2026-09-08-m3-givens-q/progress.md` for the measured ratios.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `GivensQ`, the second `AbstractQRep`, and make `UpdatableQR` and its four column verbs work against either representation, so a QR factorization can be built, updated and solved without ever forming `Q`.

**Architecture:** `GivensQ` holds the standard library's own implicit orthogonal factor — the reflector product inside a `QR` or `QRCompactWY` — followed by a log of plane rotations. The thin factor is the leading `n` columns of that `m x m` product, and the columns past `n` are the orthonormal complement that column-appending verbs draw on. A verb that would rotate two columns of an explicit `Q` instead appends one entry to the log, which is `O(1)` rather than `O(m)`; the price is that every application of `Q` walks the log. `GivensQ` does **not** save memory over a thin `DenseQ` at construction — both are `O(mn)` — and its log then grows with every verb. What it saves is the cost of forming `Q`, measured in `docs/superpowers/specs/RESULTS.md`: `geqrf` alone is 196 ms at n=2000 and 1578 ms at n=4000, and `geqrf` followed by `Matrix(F.Q)` is 493 ms and 3958 ms, so forming the thin factor adds 297 ms and 2380 ms — about 1.5x the cost of the factorization it comes from, taking the pair to about 2.5x `geqrf` alone. What grows is application cost, so the representation carries a compaction policy: `materialize` converts to a `DenseQ`, and `compaction_due` reports when the log has grown past the measured threshold.

The bulk of this milestone is not `GivensQ` itself. M2b's verbs dispatch on `<:DenseQ` and reach explicit storage through `_active`, `_augmented` and `_spare`, which are not contract methods. Making them work for a second representation means widening `AbstractQRep`'s contract with the operations those verbs actually need and rewriting each verb against them. Tasks 7 and 8 are that conversion; Tasks 3-6 are the new representation.

Because that conversion rewrites verified verbs, and because applying a `GivensQ` is slower than applying a `DenseQ` from the first application onward, the milestone is gated on a measurement of the consumer's own loop before any of it starts. Task 2 times an active-set working-set change — build, then column insertions and deletions interleaved with solves — for both representations, and states the ratio at which M3 proceeds. A gate that fails ends the milestone by removing the `AbstractQRep` seam instead of widening it.

**Tech Stack:** Julia 1.12, `LinearAlgebra`, `TypeContracts` 0.14, `StrictModeTest` 0.4.2 and `JSON` (test only), `TestItems`/`TestItemRunner`, `Chairmarks` and `JSON` (bench only), DocumenterVitepress.

**Spec:** `docs/superpowers/specs/2026-09-08-updatablefactorizations-design.md`, section 4 ("Q representations"), section 7, section 9, and milestone M3 in section 12. Requirement R8; the `AbstractQRep` half of R9 and R10; R11 and R15 for the routines added here.

```julia
@contract AbstractQRep{T} "The orthonormal factor of an UpdatableQR." begin
    Base.size(::Self)::Tuple{Int, Int}    => "the shape of the active factor"
    Base.copyto!(::AbstractMatrix, ::Self) => "write the active factor densely"
    materialize(::Self)                    => "an explicitly stored equivalent"
    LinearAlgebra.lmul!(::Givens, ::Self)  => "apply a rotation on the left"
    LinearAlgebra.rmul!(::Self, ::Givens)  => "apply a rotation on the right"
end

Base.eltype(::AbstractQRep{T}) where {T} = T
Base.Matrix(q::AbstractQRep{T}) where {T} = copyto!(Matrix{T}(undef, size(q)), q)
Base.size(q::AbstractQRep, dim::Integer)   # throws "dimension must be positive, got $dim"

mutable struct DenseQ{T, S <: AbstractMatrix{T}} <: AbstractQRep{T}
    buf::S
    m::Int
    n::Int
end
DenseQ{T, S}(buf, m, n)      # the only constructor; there is no single-matrix form

_active(q::DenseQ)     # view(q.buf, 1:q.m, 1:q.n)
_augmented(q::DenseQ)  # view(q.buf, 1:q.m, 1:(q.n + 1))
_spare(q::DenseQ)      # view(q.buf, 1:q.m, q.n + 1)
capacity(q::DenseQ)    # (size(q.buf, 1), size(q.buf, 2) - 1)
materialize(q::DenseQ) = q               # returns itself; it does not copy
_insertrow!(q::DenseQ, i)                # takes no vector
_deleterow!(q::DenseQ, i)
_dropcolumn!(q::DenseQ)                  # the drop verb; there is no `_shrink!`
_clearspare!(q::DenseQ)

mutable struct UpdatableQR{T, S <: AbstractMatrix{T}, Q <: AbstractQRep{T}} <: Factorization{T}
    qrep::Q
    factors::S
    m::Int
    n::Int
    work::Vector{T}
    corr::Vector{T}
end
UpdatableQR(G::Union{QR{T}, QRCompactWY{T}}; capacity = (2size(G, 1), 2size(G, 2)))
UpdatableQR(A::AbstractMatrix; capacity = (2size(A, 1), 2size(A, 2)))

_upper(F)   # view(F.factors, 1:F.n, 1:F.n)
_raug(F)    # view(F.factors, 1:(F.n + 1), 1:F.n)
_rspare(F)  # view(F.factors, 1:F.n, F.n + 1)
capacity(F::UpdatableQR) = capacity(getfield(F, :qrep))
Base.getproperty(F::UpdatableQR{T, S, <:DenseQ}, s)   # :Q -> _active(qrep), :R -> UpperTriangular
Base.AbstractMatrix(F::UpdatableQR) = F.Q * F.R
_grow!(F::UpdatableQR{T, S, <:DenseQ}, mneeded, nneeded)
_project!(w, r, Qa, corr)            # two Gram-Schmidt passes; returns norm(r)
_project_residual!(w, r, Qa, corr)   # the second pass alone
_retriangularize!(Rv::AbstractMatrix{T}, q::AbstractQRep{T})   # already representation-generic
```

Four facts about that interface drive this plan:

1. There is no `_apply!`, no `_applyadj!`, no `_augment!` and no `_shrink!`. The names M2b ships
   for the two operations that do exist are `_dropcolumn!` and `_clearspare!`.
2. `UpdatableQR` has six fields, named `qrep`, `factors`, `m`, `n`, `work`, `corr`. `work` is a
   `Vector`, not a `Matrix`. M2b's ledger records the divergence from the spec sketch.
   `getproperty` is intercepted for `:Q` and `:R`, so `getfield(F, :Q)` never resolves; internal
   code reads `getfield(F, :qrep)`.
3. There is no representation-selecting constructor in any spelling. `UpdatableQR(::QR)`
   hardcodes `DenseQ{T, Matrix{T}}`, and `getproperty`, `_grow!`, `lowrankupdate!`,
   `insert_column!`, `delete_column!` and `shift_columns!` are all specialized on `<:DenseQ`.
4. The verbs reach storage through `_active`, `_augmented` and `_spare`. An implicit factor has
   none of those, so the verbs must be rewritten against operations both representations can
   answer.

## Buffer map

`GivensQ` owns two buffers and aliases a third it does not own. Publish the map before writing
the code, because an aliasing mistake here is a wrong answer that no allocation test catches.

| buffer | length | written by | lifetime |
| --- | --- | --- | --- |
| `work` | `m` | `_apply!`, `_applyadj!`, `_augment!`, `_project!` | consumed within a single call; never live across two |
| `resid` | `m` | the calling verb, through `_scratch` | one verb; zero on entry and on exit |
| `base` | — | not written | shared with the factorization it was built from |

`base` is `F.Q` of the `QR` or `QRCompactWY` handed to the constructor, which is itself a view
over that factorization's `factors` and `T` arrays. The representation therefore reads the
caller's factorization for its whole lifetime; mutating those arrays afterwards changes what the
representation stands for. `GivensQ`'s docstring says so.

`resid` is `GivensQ`'s answer to `_scratch`, the `m`-length column every verb builds a direction
in. `DenseQ`'s answer is `_spare(q)`, the augmentation column M2b's buffer map already accounts
for, so the `DenseQ` path gains no storage from this milestone.

The rule that follows: a caller must not pass a view of `Q.work` as the `x`, `z` or `r` argument
of any routine here. `_scratch(q)` is `resid`, never `work`, so the verbs satisfy the rule by
construction.

The rotation log (`plane`, `cosines`, `sines`) grows with `push!` and is never scratch.

#### Ruling 1: how `GivensQ` reaches the verbs

M2b's `@contract AbstractQRep` has five clauses — `size`, `copyto!`, `materialize`,
`lmul!(::Givens, ::Self)`, `rmul!(::Self, ::Givens)` — and none of them is what the verbs
actually call. `lowrankupdate!` and `insert_column!` call `mul!` against `_active(q)` and build
a direction in `_spare(q)`; `delete_column!` calls `_dropcolumn!(q)`. An implicit factor has no
`_active` and no `_spare`.

| option | consequence |
| --- | --- |
| A | Express `GivensQ` behind the existing five clauses. Not reachable: the verbs do not go through those clauses, so this would mean `GivensQ` conforms to the contract and still cannot be used by any verb. |
| B (recommended) | Widen the contract with the operations the verbs need — `_applyadj!`, `_scratch`, `_project!`, `_augment!`, `_clearaug!`, `_promote!`, `_dropcolumn!` — give `DenseQ` those methods over its existing storage helpers, and rewrite the four supported verbs against them. |

Option B is what the rest of this plan is written for. It means M3 owns re-plumbing M2b's verbs,
which is Tasks 7 and 8 and is the larger half of the milestone.

The seven added operations, and why each is there:

| operation | called by |
| --- | --- |
| `_applyadj!(y, q, z)` | `ldiv!(y, F, b)`, `ldiv!(F, B)` |
| `_scratch(q)` | `lowrankupdate!`, `insert_column!` — the `m`-length column a direction is built in |
| `_project!(w, q, corr)` | `lowrankupdate!`, `insert_column!` — two Gram-Schmidt passes over `_scratch(q)` |
| `_augment!(q, r)` | `lowrankupdate!`, `insert_column!` — make the augmentation column the direction of `r` |
| `_clearaug!(q)` | `lowrankupdate!`, `insert_column!` — return the augmentation column to zero |
| `_promote!(q)` | `insert_column!` — adopt the augmentation column as column `n+1` |
| `_dropcolumn!(q)` | `delete_column!` — M2b's own name, kept |

`_apply!(y, q, x)` is defined for both representations and used by their `_project!` methods and
by the tests, but it is not a contract clause: no verb calls it polymorphically.

#### Ruling 2: what `F.Q` is when the representation is not explicit

M2b documents `F.Q` as "a view of live storage". A `GivensQ` has no such view, and producing one
means forming `Q`, which is the cost the representation exists to avoid.

| option | consequence |
| --- | --- |
| A | `F.Q` forms and returns a dense matrix for a `GivensQ`. Silently `O(mn)` on a property access, and it defeats the representation. |
| B (recommended) | `getproperty(F::UpdatableQR{T, S, <:DenseQ}, :Q)` keeps M2b's view. For any other representation `F.Q` returns the representation object itself, and `Matrix(F.Q)` is the explicit form. `Base.AbstractMatrix(F)` becomes `Matrix(getfield(F, :qrep)) * F.R`, which is correct for both and costs the `DenseQ` path one extra `m x n` copy in a routine that already allocates its product. |

Under Option B, `F.Q` has different types for the two representations. That is visible to a
caller and belongs in the `UpdatableQR` docstring and on the Q representations page.

#### Ruling 3: `lmul!(::Givens, ::GivensQ)`

The log records rotations applied on the *right*. A left multiplication `Q <- G*Q` cannot be
appended to it: it acts on the row space, which is the same reason `insert_row!` and
`delete_row!` are refused. `lmul!(G, q::DenseQ)` is defined and tested in M2b but is called by no
verb.

| option | consequence |
| --- | --- |
| A | Keep `lmul!` a mandatory contract clause and give `GivensQ` a method that always throws. `@verify GivensQ` passes, but the contract then asserts an operation one implementation cannot perform. |
| B (recommended) | Move `lmul!(::Givens, ::Self)` into the contract's `:optional` group, and give `GivensQ` a method that throws with a message naming `materialize`. `@verify DenseQ` is unaffected — a satisfied optional clause is still satisfied — and the contract stays true. |

- [ ] **Step 4: Write the decision sweep**

Applying a `GivensQ` is slower than applying a `DenseQ` from the first application onward, and
the log makes it slower still with every verb. The whole representation therefore rests on one
arithmetic: the formation cost it never pays has to outweigh the application cost it adds, over
the run of verbs and solves a caller actually performs. The named consumer is an active-set QP
solver, which inserts or deletes a column and then solves, repeatedly. That loop is what this
sweep times, before any shipped verb is touched.

The `DenseQ` arm is the shipped `UpdatableQR`. The `GivensQ` arm is `proto_givensq.jl`'s
kernels, which Tasks 3-5 ship unchanged, driving the same `R`-side work: a column insertion
costs one `applyadj!`, one `apply!`, one `augment!` and a rank-1 update of `R`; a column
deletion costs the same retriangularization sweep as the dense verb, with each rotation pushed
onto the log rather than applied to two stored columns; a solve costs one `applyadj!` and one
triangular solve. The `R`-side work is identical in both arms and is included in both, because
the ratio a caller sees is over the whole loop and not over the `Q` half of it.

M1 creates `bench/Project.toml` with `Chairmarks`, `JSON`, `LinearAlgebra`, `Random` and the
package by path, which is everything this sweep needs; add anything missing with `Pkg.add` and a
matching `Pkg.compat`, never a hand-written UUID, and never `QRupdatesFast` — this environment

`bench/givensq_decision.jl`:

```julia
# Whole-loop cost of an active-set working-set change: build the factorization, then alternate
# column insertions and deletions with solves. The representations differ in where the cost of
# the orthonormal factor falls -- formed once and applied cheaply, or never formed and applied
# through a growing rotation log -- so only the total over a run decides between them.
using LinearAlgebra, Random, Chairmarks, JSON
using UpdatableFactorizations

include(joinpath(@__DIR__, "..", "docs", "superpowers", "specs", "proto_givensq.jl"))

BLAS.set_num_threads(1)

function dense_loop(A, xs, bs)
    m, n = size(A)
    F = UpdatableQR(A; capacity = (m, n + length(xs)))
    s = 0.0
    for k in eachindex(xs)
        insert_column!(F, size(F, 2) + 1, xs[k])
        s += sum(F \ bs[k])
        delete_column!(F, 1)
        s += sum(F \ bs[k])
    end
    return s
end

function givens_loop(A, xs, bs)
    m, n = size(A)
    G = qr(A)
    Q = GQ(G)
    R = Matrix(G.R)
    w = zeros(eltype(A), m)
    y = zeros(eltype(A), m)
    s = 0.0
    for k in eachindex(xs)
        # Insertion: the projection, the new direction, and the widened triangle.
        applyadj!(view(w, 1:Q.n), Q, xs[k])
        apply!(y, Q, view(w, 1:Q.n))
        r = xs[k] - y
        beta = augment!(Q, r)
        R = [R view(w, 1:(Q.n - 1)); zeros(1, Q.n - 1) beta]
        s += sum(UpperTriangular(R) \ (applyadj!(zeros(Q.n), Q, bs[k])))
        # Deletion of the leading column: drop it and retriangularize, pushing each rotation.
        R = R[:, 2:end]
        for i in 1:(size(R, 2))
            H, _ = LinearAlgebra.givens(R[i, i], R[i + 1, i], i, i + 1)
            lmul!(H, R)
            push_rot!(Q, Givens(H.i1, H.i2, real(H.c), -H.s))
        end
        R = R[1:(end - 1), :]
        Q.n -= 1
        s += sum(UpperTriangular(R) \ (applyadj!(zeros(Q.n), Q, bs[k])))
    end
    return s
end

function cell(m, n, k; samples = 20)
    Random.seed!(20260908)
    A = randn(m, n)
    xs = [randn(m) for _ in 1:k]
    bs = [randn(m) for _ in 1:k]
    dense_loop(A, xs, bs)
    givens_loop(A, xs, bs)
    td = minimum(@be dense_loop($A, $xs, $bs) evals = 1 samples = samples).time
    tg = minimum(@be givens_loop($A, $xs, $bs) evals = 1 samples = samples).time
    return Dict("m" => m, "n" => n, "k" => k, "dense" => td, "givens" => tg, "ratio" => td / tg)
end

# Shapes an active-set QP solver reaches: many more rows than working-set columns, and a
# working set that turns over on the order of once per column.
shapes = ((400, 50), (800, 100), (2000, 200))
rows = [cell(m, n, k) for (m, n) in shapes for k in (n ÷ 4, n ÷ 2, n)]
```

```julia
"""
    GivensQ(F::QR; compact)
    GivensQ(F::QRCompactWY; compact)

Orthonormal factor of a thin QR factorization, held as the factorization's own implicit factor
followed by a log of plane rotations. `Q` is never formed: `Matrix(Q)` and `materialize(Q)` form
it on demand.

The thin factor is the leading `n` columns of an `m x m` orthogonal product, and the columns
past `n` are the orthonormal complement that column insertion draws on. Storage is
`O(mn + nrotations(Q))`: the implicit base factor, plus three entries per logged rotation. Each
modification appends between `n` and `m` rotations, so the log grows without bound until it is
compacted. `compact` is the number of rotations per column past which the log is due for
compaction: `compaction_due(Q)` reports it, and `materialize` performs it.

The implicit base factor is `F.Q`, which is a view over `F`'s own arrays. It is shared, not
copied: writing to `F` after construction changes what this representation stands for.

Row insertion and deletion are not supported, and neither is left multiplication by a rotation,
because every rotation in the log is indexed against a fixed set of rows. `materialize` first.

Givens, *Computation of plane unitary rotations transforming a general matrix to triangular
form*, Journal of the Society for Industrial and Applied Mathematics 6 (1958), 26-50. The use of
a stored rotation product as a factorization's orthonormal factor under modification follows
Gill, Golub, Murray and Saunders, *Methods for modifying matrix factorizations*, Mathematics of
Computation 28 (1974), 505-535.
"""
mutable struct GivensQ{T, R <: Real, B} <: AbstractQRep{T}
    base::B              # implicit m x m orthogonal factor, applied without being formed
    plane::Vector{Int}   # rotation k acts in the (plane[k], plane[k] + 1) plane
    cosines::Vector{R}   # rotation k's cosine, real for every element type
    sines::Vector{T}     # rotation k's sine
    work::Vector{T}      # scratch of length m, consumed in place by every application
    resid::Vector{T}     # the direction a verb builds; zero on entry to and exit from a verb
    m::Int
    n::Int
    compact::Int         # the log is due for compaction past compact * n rotations
end

function GivensQ(F::Union{QR{T}, QRCompactWY{T}}; compact::Int) where {T}
    compact >= 1 || throw(ArgumentError("compact is $compact, it must be at least 1"))
    m, n = size(F)
    m >= n || throw(DimensionMismatch("factorization is $(m)x$(n); it requires m >= n"))
    R = real(T)
    Q = F.Q
    return GivensQ{T, R, typeof(Q)}(
        Q, Int[], R[], T[], zeros(T, m), zeros(T, m), m, n, compact
    )
end

Base.size(Q::GivensQ) = (Q.m, Q.n)

"""
    nrotations(Q::GivensQ) -> Int

Number of plane rotations in the log. It grows by up to `m` per modification of the
factorization and is reset only by `materialize`.
"""
nrotations(Q::GivensQ) = length(Q.plane)

# Rotation k of the log. The adjoint of a plane rotation with a real cosine negates the sine.
_rotation(Q::GivensQ{T}, k::Int) where {T} =
    Givens(Q.plane[k], Q.plane[k] + 1, T(Q.cosines[k]), Q.sines[k])
_rotation_adj(Q::GivensQ{T}, k::Int) where {T} =
    Givens(Q.plane[k], Q.plane[k] + 1, T(Q.cosines[k]), -Q.sines[k])

function _apply!(y::AbstractVector, Q::GivensQ{T}, x::AbstractVector) where {T}
    length(y) == Q.m ||
        throw(DimensionMismatch("y has length $(length(y)), the factor has $(Q.m) rows"))
    length(x) == Q.n ||
        throw(DimensionMismatch("x has length $(length(x)), the factor has $(Q.n) columns"))
    t = Q.work
    copyto!(view(t, 1:Q.n), x)
    fill!(view(t, (Q.n + 1):Q.m), zero(T))
    for k in nrotations(Q):-1:1
        lmul!(_rotation(Q, k), t)
    end
    lmul!(Q.base, t)
    copyto!(y, t)
    return y
end

function _applyadj!(y::AbstractVector, Q::GivensQ, z::AbstractVector)
    length(z) == Q.m ||
        throw(DimensionMismatch("z has length $(length(z)), the factor has $(Q.m) rows"))
    length(y) == Q.n ||
        throw(DimensionMismatch("y has length $(length(y)), the factor has $(Q.n) columns"))
    t = Q.work
    copyto!(t, z)
    lmul!(Q.base', t)
    for k in 1:nrotations(Q)
        lmul!(_rotation_adj(Q, k), t)
    end
    copyto!(y, view(t, 1:Q.n))
    return y
end

# Forming the factor is the log applied in reverse to the leading columns of an identity,
# followed by the base factor. Rotations act on rows, so an m x n target is enough.
function Base.copyto!(A::AbstractMatrix, Q::GivensQ{T}) where {T}
    size(A) == (Q.m, Q.n) || throw(
        DimensionMismatch("target is $(size(A)), the factor is $(Q.m)x$(Q.n)")
    )
    Base.require_one_based_indexing(A)
    fill!(A, zero(T))
    for i in 1:Q.n
        A[i, i] = one(T)
    end
    for k in nrotations(Q):-1:1
        lmul!(_rotation(Q, k), A)
    end
    lmul!(Q.base, A)
    return A
end

"""
    materialize(Q::GivensQ) -> DenseQ

Form the explicit thin factor and return it as a `DenseQ`. `Q` is left as it was, and the result
shares no storage with it.

The buffer carries the augmentation column every updating verb builds in, so the result is a
factor the verbs can be run against immediately. Its capacity is exactly `(m, n)`, so the next
column insertion grows it.

The cost is that of forming a thin `Q` from a Householder factorization plus one pass of the log
over `n` columns.
"""
function materialize(Q::GivensQ{T}) where {T}
    buf = zeros(T, Q.m, Q.n + 1)
    copyto!(view(buf, 1:Q.m, 1:Q.n), Q)
    return DenseQ{T, Matrix{T}}(buf, Q.m, Q.n)
end
```

```julia
"""
    rmul!(Q::GivensQ, G::Givens) -> Q

Append `G` to the rotation log, which is what right multiplication by a plane rotation costs
here: `O(1)` rather than the `O(m)` of rotating two stored columns.

The log records one index per rotation, so `G` must act in a pair of adjacent planes. Every
rotation a QR modification produces does.
"""
function LinearAlgebra.rmul!(Q::GivensQ, G::Givens)
    G.i2 == G.i1 + 1 || throw(
        ArgumentError(
            "rotation acts in the ($(G.i1), $(G.i2)) plane; the log holds adjacent planes only"
        )
    )
    1 <= G.i1 && G.i2 <= Q.m || throw(BoundsError(Q, G.i2))
    push!(Q.plane, G.i1)
    push!(Q.cosines, real(G.c))
    push!(Q.sines, G.s)
    return Q
end

# The dropped column stays in the implicit complement, so nothing is lost and nothing is copied.
function _dropcolumn!(Q::GivensQ)
    Q.n > 0 || throw(DimensionMismatch("the factor has no column to drop"))
    Q.n -= 1
    return Q
end
```

These five operations are the seam Ruling 1 chose. Each has a one-line `DenseQ` method over
M2b's existing storage helpers and a real implementation for `GivensQ`.

`_augment!(q, r) -> beta` makes the augmentation column — column `n+1` of the basis every verb
works in — the direction of `r`, so that `q_{n+1} * beta == r`. It does **not** change `n`;
`_promote!` does that, and only `insert_column!` calls it. `abs(beta)` is `norm(r)`. Returning
`beta` rather than assuming `norm(r)` is what lets the rotations pick the direction: for
`GivensQ` the appended column is whatever the complement rotates onto, and `beta` carries the
phase.

`r` must be orthogonal to the existing columns. The verbs satisfy that by calling `_project!`
first, but the routine checks it rather than trusting it: a residual with a component inside the
range yields a `beta` that violates the routine's contract while every orthogonality assertion in
the suite still passes. Measured at `m, n = 10, 4` with `r + 0.5 * Q[:, 1]` in place of `r`:
`norm(M[:, n+1] * beta - r) / norm(r)` is 0.21 and `abs(abs(beta) - norm(r)) / norm(r)` is
0.023, while `norm(M' * M - I)` stays at 4.4e-16. `rtol` is the relative threshold on the range
component, spelled as `insert_column!` spells its own.

```julia
# The operations the updating verbs call polymorphically. DenseQ answers each one over the
# storage it already has: the augmentation column is both its scratch and the column a verb
# builds its new direction in.
_scratch(q::DenseQ) = _spare(q)
_clearaug!(q::DenseQ) = _clearspare!(q)
_promote!(q::DenseQ) = (q.n += 1; q)

_apply!(y::AbstractVector, q::DenseQ, x::AbstractVector) = mul!(y, _active(q), x)
_applyadj!(y::AbstractVector, q::DenseQ, z::AbstractVector) = mul!(y, _active(q)', z)

    _project!(w, _spare(q), _active(q), corr)

# `r` is `_spare(q)` and is normalized in place, so the augmentation column becomes the unit
# direction and the returned scale is its norm.
function _augment!(q::DenseQ{T}, r::AbstractVector; rtol::Real = sqrt(eps(real(T)))) where {T}
    length(r) == q.m ||
        throw(DimensionMismatch("r has length $(length(r)), the factor has $(q.m) rows"))
    q.n < q.m || throw(
        DimensionMismatch("the $(q.m) by $(q.n) factor has no column to append")
    )
    beta = norm(r)
    iszero(beta) && throw(
        ArgumentError("the residual lies in the range of the factor; there is no column to append")
    )
    inside = norm(mul!(similar(r, q.n), _active(q)', r))
    inside <= rtol * beta || throw(
        ArgumentError(
            "the residual is not orthogonal to the factor: its component in the range is " *
                "$inside against a norm of $beta"
        )
    )
    r ./= beta
    return beta
end
```

```julia
_scratch(Q::GivensQ) = Q.resid
_clearaug!(Q::GivensQ{T}) where {T} = (fill!(Q.resid, zero(T)); Q)
_promote!(Q::GivensQ) = (Q.n += 1; Q)

# Two Gram-Schmidt passes against the implicit factor. One pass leaves orthogonality at
# sqrt(eps)/gamma, which collapses on an ill-conditioned factor; two hold it at O(eps).
#
# Giraud, Langou and Rozlozník, *The loss of orthogonality in the Gram-Schmidt orthogonalization
# process*, Computers and Mathematics with Applications 50 (2005), 1069-1075.
function _project!(w::AbstractVector, Q::GivensQ, corr::AbstractVector)
    r = Q.resid
    _applyadj!(w, Q, r)
    t = Q.work                      # free again: _applyadj! consumed and released it
    _apply!(t, Q, w)
    r .-= t
    _applyadj!(corr, Q, r)
    _apply!(t, Q, corr)
    r .-= t
    w .+= corr
    return norm(r)
end

"""
    _augment!(Q::GivensQ, r; rtol = sqrt(eps(real(T)))) -> beta

Make the augmentation column — column `n+1` of the basis the updating verbs work in — the
direction of `r`, so that it times `beta` is `r`. `abs(beta)` is `norm(r)`. `r` is not modified,
and the column count is unchanged; `_promote!` adopts the column.

`r` must be orthogonal to the existing columns and nonzero. `ArgumentError` is thrown when its
component inside the range exceeds `rtol * norm(r)`, because a residual that fails this yields a
`beta` that misses `r` by that fraction while the factor stays orthonormal, which no
reconstruction or orthogonality check detects.

The new column comes out of the orthonormal complement the representation already carries:
expressing `r` in the implicit factor's own basis leaves a vector supported on columns `n+1:m`,
and `m-n-1` rotations concentrate it on column `n+1`.

Daniel, Gragg, Kaufman and Stewart, *Reorthogonalization and stable algorithms for updating the
Gram-Schmidt QR factorization*, Mathematics of Computation 30 (1976), 772-795.
"""
function _augment!(Q::GivensQ{T}, r::AbstractVector; rtol::Real = sqrt(eps(real(T)))) where {T}
    length(r) == Q.m ||
        throw(DimensionMismatch("r has length $(length(r)), the factor has $(Q.m) rows"))
    Q.n < Q.m || throw(
        DimensionMismatch("the $(Q.m) by $(Q.n) factor has no column to append")
    )
    c = Q.work
    copyto!(c, r)
    lmul!(Q.base', c)
    for k in 1:nrotations(Q)
        lmul!(_rotation_adj(Q, k), c)
    end
    outside = norm(view(c, (Q.n + 1):Q.m))
    iszero(outside) && throw(
        ArgumentError("the residual lies in the range of the factor; there is no column to append")
    )
    inside = norm(view(c, 1:Q.n))
    inside <= rtol * norm(r) || throw(
        ArgumentError(
            "the residual is not orthogonal to the factor: its component in the range is " *
                "$inside against a norm of $(norm(r))"
        )
    )
    for i in (Q.m - 1):-1:(Q.n + 1)
        G, _ = givens(c[i], c[i + 1], i, i + 1)
        lmul!(G, c)
        rmul!(Q, Givens(G.i1, G.i2, G.c, -G.s))
    end
    return c[Q.n + 1]
end

_augment!(Q::GivensQ, r::AbstractVector, ::AbstractVector; rtol = sqrt(eps(real(eltype(Q))))) =
    _augment!(Q, r; rtol)
```

so a refused call leaves the factor and the log exactly as they were.

```julia
# Structural only. Orthonormality is a numerical property of the factor the test items check
# directly, and asserting it here would materialize the whole factor on every invariant check.
@invariants GivensQ begin
    "the rotation log's arrays agree in length" =>
        Q -> length(Q.plane) == length(Q.cosines) == length(Q.sines)
    "every rotation acts on a pair of rows" =>

    "every rotation is unitary" =>
        Q -> all(

        eachindex(Q.plane)
    )

    "the workspaces cover the row space" =>
        Q -> length(Q.work) >= Q.m && length(Q.resid) >= Q.m
    "the base factor spans the row space" => Q -> size(Q.base, 1) == Q.m
end

@verify GivensQ
```

```julia
# Grow the triangular buffer to hold nneeded columns, doubling if it is exceeded. Returns true
# when the buffer was rebound, so a caller holding a view of it knows the view is stale.
function _growr!(F::UpdatableQR{T}, nneeded::Int) where {T}
    ncap = size(getfield(F, :factors), 1) - 1
    nneeded <= ncap && return false
    newn = max(nneeded, 2ncap)
    rbuf = zeros(T, newn + 1, newn + 1)
    copyto!(view(rbuf, 1:F.n, 1:F.n), _upper(F))
    F.factors = rbuf
    resize!(F.work, newn + 1)
    resize!(F.corr, newn + 1)
    return true
end

# A GivensQ stores no factor, so only the triangular buffer grows. Row growth cannot happen:
# the verbs that would cause it are refused.
function _grow!(F::UpdatableQR{T, S, <:GivensQ}, mneeded::Int, nneeded::Int) where {T, S}
    mneeded <= F.m || throw(
        DimensionMismatch(
            "growing to $mneeded rows is not supported on a GivensQ factor: its $(F.m) rows " *
                "are fixed by the rotation log; call materialize first"
        )
    )
    _growr!(F, nneeded)
    return F
end
```

M2b's `_grow!(F::UpdatableQR{T, S, <:DenseQ}, ...)` keeps its Q-buffer half and delegates its R

```julia
"""
    materialize(F::UpdatableQR) -> UpdatableQR

Return the factorization with its orthonormal factor stored explicitly. `F` is left as it was,
and the returned factorization shares no storage with it.

It returns a new factorization rather than modifying this one, because the representation is
part of the factorization's type. The `Q` buffer is sized exactly, so the next column insertion
grows it.
"""
function materialize(F::UpdatableQR{T}) where {T}
    q = getfield(F, :qrep)
    buf = zeros(T, q.m, q.n + 1)
    copyto!(view(buf, 1:q.m, 1:q.n), q)
    D = DenseQ{T, Matrix{T}}(buf, q.m, q.n)
    return UpdatableQR{T, Matrix{T}, typeof(D)}(
        D, copy(getfield(F, :factors)), F.m, F.n,
        copy(getfield(F, :work)), copy(getfield(F, :corr))
    )
end
```

It builds the buffer itself rather than calling `materialize(getfield(F, :qrep))`, because
`materialize(q::DenseQ)` returns `q` and the copy would then alias `F`.

- [ ] **Step 3: Rewrite `lowrankupdate!`**

Drop the `<:DenseQ` constraint and replace the storage accesses. The algebra, the messages, the
`rho` threshold and the docstring are unchanged; what changes is how the routine reaches the

```julia
function LinearAlgebra.lowrankupdate!(
        F::UpdatableQR{T}, u::AbstractVector, v::AbstractVector
    ) where {T}
    m, n = F.m, F.n
    length(u) == m ||
        throw(DimensionMismatch("u has length $(length(u)), factorization is $(m)x$(n)"))
    length(v) == n ||
        throw(DimensionMismatch("v has length $(length(v)), factorization is $(m)x$(n)"))
    q = getfield(F, :qrep)
    r = _scratch(q)
    z = view(F.work, 1:(n + 1))
    w = view(z, 1:n)
    corr = view(F.corr, 1:n)
    iu = firstindex(u) - 1
    for i in 1:m
        r[i] = u[iu + i]
    end
    unrm = norm(r)
    rho = _project!(w, q, corr)
    RA = _raug(F)
    if m > n && rho > n * eps(real(T)) * unrm
        z[n + 1] = _augment!(q, r, corr)
        last = n + 1
    else
        _clearaug!(q)
        z[n + 1] = zero(T)
        last = n
    end
    for k in (last - 1):-1:1
        c, s, rr = givensAlgorithm(z[k], z[k + 1])
        G = Givens(k, k + 1, oftype(z[k], c), oftype(z[k], s))
        z[k] = rr
        z[k + 1] = zero(T)
        lmul!(G, RA)
        rmul!(q, G')
    end
    iv = firstindex(v) - 1
    for j in 1:n
        RA[1, j] += z[1] * conj(v[iv + j])
    end
    _retriangularize!(RA, q)
    _clearaug!(q)
    for j in 1:n
        RA[n + 1, j] = zero(T)
    end
    return F
end
```

Three differences from M2b's body, each a consequence of the seam:

- `Qa = _active(q)` is gone; `_project!(w, q, corr)` does the two passes against whatever the
  representation is.
- `r ./= rho; z[n + 1] = rho` becomes `z[n + 1] = _augment!(q, r, corr)`. `abs` of the returned
  scale is `rho`; a `GivensQ`'s appended column carries a phase, and the scale carries it back.
  `corr` is reused as the guard's workspace, which is free at this point.
- `_clearspare!(q)` becomes `_clearaug!(q)`, in the negligible-residual branch as well as at the
  end, and it is what returns the scratch column to zero.

`rmul!(q, G')` is unchanged and is where a `GivensQ` records instead of rotating.

- [ ] **Step 4: Rewrite `insert_column!`**

```julia
function insert_column!(
        F::UpdatableQR{T}, j::Integer, x::AbstractVector;
        rtol::Real = sqrt(eps(real(T)))
    ) where {T}
    m, n = F.m, F.n
    1 <= j <= n + 1 || throw(BoundsError(F, j))
    length(x) == m ||
        throw(DimensionMismatch("x has length $(length(x)), factorization is $(m)x$(n)"))
    m > n || throw(
        DimensionMismatch(
            "inserting a column would leave a $(m)x$(n + 1) factorization; " *
                "the factorization requires m >= n"
        )
    )
    q = getfield(F, :qrep)
    r = _scratch(q)
    w = view(F.work, 1:n)
    corr = view(F.corr, 1:n)
    ix = firstindex(x) - 1
    for i in 1:m
        r[i] = x[ix + i]
    end
    xnrm = norm(r)
    rho = _project!(w, q, corr)
    if !(rho > rtol * xnrm)
        # The projection built the candidate direction in the augmentation column. Clearing it
        # is what leaves the factorization as it was, and the next verb builds there.
        _clearaug!(q)
        throw(ArgumentError("column $j lies in the range of the existing columns: rho = $rho"))
    end
    beta = _augment!(q, r, corr)
    # Growth comes after the guard, so a rejected insertion does not change the capacity. It
    # carries the augmentation column across, so the direction survives it; every view above
    # does not.
    _grow!(F, m, n + 1)
    R = getfield(F, :factors)
    for k in 1:n
        R[k, n + 1] = w[k]
    end
    R[n + 1, n + 1] = beta
    F.n = n + 1
    _promote!(q)
    return j == n + 1 ? F : shift_columns!(F, n + 1, Int(j))
end
```

`R[n+1, n+1]` holds `beta` rather than `rho`. For a `DenseQ` the two are the same real number;
for a `GivensQ` `beta` carries the phase of the appended column, and the reconstruction is only
exact with it. The docstring's sentence "its norm `rho` becomes the new diagonal entry of `R`"
becomes "its scale becomes the new diagonal entry of `R`, whose absolute value is `rho`", and
the `rtol` paragraph is unchanged.

`w` must be read out of `F.work` before `_grow!` resizes it. It is: the loop that copies `w`
into `R` runs after `_grow!`, and `resize!` on a `Vector` preserves the leading entries, but the
*view* `w` is invalidated by the `resize!`. Take the values out before the growth, or re-take the
view after it, and assert the result in Task 10's item — this is the failure M2b's own comment
warns about and it is easy to reintroduce here.

The threshold is measured, not chosen. Applying `Q` through the log costs the base factor's own
application plus a per-rotation term; the log has doubled the cost of every application once the
second term matches the first. The sweep measures both terms and reports that crossover as a
multiple of `n`.

The crossover scales with `m`, not with `m/n`: the base term is the cost of applying the stored
reflectors, `O(mn)`, and the per-rotation term is a constant, so `crossover/n` is proportional to
`m` and `n` cancels. Measured at 200 reps on an unpinned-clock host: 106, 97, 150 and 315 for
`(m, n) = (500, 50), (500, 100), (1000, 50), (1000, 100)`. Halving `n` barely moves it; doubling
`m` roughly doubles it. A single default is therefore a floor, calibrated at the smallest `m` in
the sweep, and both the docstring and the docs page say so. A caller at a larger `m` who wants
the crossover for their own shape passes `compact`.

```julia
# Cost of applying a GivensQ as its rotation log grows, against the same factor stored densely.
# Run on this development machine; the samples are read back from results/, never re-measured.
using LinearAlgebra, Random, Chairmarks, JSON
using UpdatableFactorizations: GivensQ, materialize, _apply!

BLAS.set_num_threads(1)

# A real log comes from retriangularization sweeps walking contiguous planes, so the fixture
# walks them too: a uniformly random plane per rotation measures a different memory pattern
# from the one the compaction policy governs.
function pushsweep!(Q, m, k)
    i = 1
    for _ in 1:k
        G, _ = LinearAlgebra.givens(randn(), randn(), i, i + 1)
        rmul!(Q, G)
        i = i == m - 1 ? 1 : i + 1
    end
    return Q
end

function sample(m, n)
    Random.seed!(20260908)
    A = randn(m, n)
    G = qr(A)
    D = Matrix(G.Q)
    x = randn(n)
    y = zeros(m)
    tdense = minimum(@be mul!($y, $D, $x)).time
    tmaterialize = minimum(@be materialize(GivensQ($G; compact = 1))).time
    lengths = [0, n, 2n, 4n, 8n, 16n, 32n, 64n]
    times = Float64[]
    for k in lengths
        Q = pushsweep!(GivensQ(G; compact = 1), m, k)
        _apply!(y, Q, x)
        push!(times, minimum(@be _apply!($y, $Q, $x)).time)
    end
    tbase = first(times)
    trot = (last(times) - first(times)) / (last(lengths) - first(lengths))
    kstar = tbase / trot
    return Dict(
        "m" => m, "n" => n, "dense" => tdense, "materialize" => tmaterialize,
        "base" => tbase, "per_rotation" => trot, "crossover" => kstar,
        "multiple" => kstar / n, "lengths" => lengths, "times" => times,
    )
end

samples = [sample(m, n) for (m, n) in ((1000, 100), (2000, 200), (4000, 400), (4000, 100))]
mkpath(joinpath(@__DIR__, "results"))
# The file is named for the host it was measured on: a crossover is a property of one machine,
# and a second host's run must not overwrite the first's.
write(
    joinpath(@__DIR__, "results", "givensq_compaction-$(gethostname()).json"),
    JSON.json(Dict("host" => gethostname(), "samples" => samples))
)

for s in samples
    println("m=", s["m"], " n=", s["n"],
        "  dense=", s["dense"], "s  base=", s["base"], "s",
        "  per-rotation=", s["per_rotation"], "s",
        "  materialize=", s["materialize"], "s",
        "  crossover=", round(Int, s["crossover"]),
        "  multiple=", round(s["multiple"], digits = 1))
end
println("compact = ", floor(Int, minimum(s["multiple"] for s in samples)))
```

````markdown
## `GivensQ`

The factorization's own implicit factor — the Householder product inside `QR` or `QRCompactWY` —
followed by a log of plane rotations. `Q` is never formed. A verb appends to the log instead of
rotating stored columns, which is `O(1)` per rotation; an application walks the log.

Forming a thin `Q` adds about 1.5 times the cost of the factorization it comes from: `geqrf`
alone is 196 ms at n=2000 and 1578 ms at n=4000, and `geqrf` followed by `Matrix(F.Q)` is 493 ms
and 3958 ms, so the formation accounts for 297 ms and 2380 ms and the pair costs about 2.5 times
`geqrf` alone. Measured single threaded on an AMD Ryzen AI 7 350. `GivensQ` avoids the formation. It does not avoid the
cost of applying `Q`, which is higher than a dense product from the first application onward, and
which grows with the log.

`F.Q` is the representation itself rather than a matrix when the factor is a `GivensQ`;
`Matrix(F.Q)` forms it. For a `DenseQ` it stays the view into live storage.

## Supported operations

| operation | `DenseQ` | `GivensQ` |
| --- | --- | --- |
| `lowrankupdate!(F, u, v)` | yes | yes |
| `insert_column!(F, j, x)` | yes | yes |
| `delete_column!(F, j)` | yes | yes |
| `shift_columns!(F, i, j)` | yes | yes |
| `F \ b`, `ldiv!` | yes | yes |
| `insert_row!(F, i, x)` | yes | throws; `materialize` first |
| `delete_row!(F, i)` | yes | throws; `materialize` first |
| `lmul!(G::Givens, q)` | yes | throws; `materialize` first |

The two row verbs change `m`, and a left rotation acts on the row space. Every rotation in the
log is a pair of row indices into a fixed row space, and row deletion additionally needs the
factor's rows one at a time, which an implicit product does not expose. All three throw with a
message naming `materialize` rather than being made silently slow.

## Compaction

Each verb appends between `n` and `m` rotations. Applying the factor costs the base factor's own
application plus a term proportional to the log's length, so past a point the log dominates.

`compaction_due(F)` reports the point at which the log has doubled the cost of an application,
and `materialize(F)` performs the conversion. It returns a new factorization rather than
modifying `F`, because the representation is part of the factorization's type:

```julia
F = UpdatableQR(A, GivensQ)
for (u, v) in updates
    lowrankupdate!(F, u, v)
    compaction_due(F) && (F = materialize(F))
end
```

The crossover is proportional to `m`, because the base term is the `O(mn)` cost of applying the
stored reflectors and the per-rotation term is a constant, so `n` cancels. The default threshold
is therefore a floor: the value measured at the smallest `m` in the sweep below. At the largest
`m` in the same sweep the true crossover is several times higher, and a caller who wants it
passes `compact` to `GivensQ`.

| m | n | dense application | base application | per rotation | materialize | crossover | crossover / n |
| --- | --- | --- | --- | --- | --- | --- | --- |

Measured single threaded on this machine; the samples are in
`bench/results/givensq_compaction-<host>.json` and the script that produced them is
`bench/givensq_compaction.jl`.

## Choosing

`GivensQ` pays when a factorization is built, modified a bounded number of times, and used for
solves, and never needs a row verb. `DenseQ` pays when applications outnumber modifications, or
when a row verb is needed. Both are slower than recomputing the factorization with LAPACK, at
every size measured; the benchmarks page carries those comparisons.
````

## Self-review

**The gate comes before the work.** Task 2 times the consumer's loop — build, then column
insertions and deletions interleaved with solves, at active-set shapes — for both
representations, and the milestone proceeds only when the implicit representation wins it by at
least 10% at one working-set change per column. Everything after Task 2 rewrites verbs that are
already verified, so the measurement that justifies rewriting them is worth more before that than
after. The no-go branch is not "do nothing": it deletes the `AbstractQRep` seam, which M2b's
self-review already sizes at one abstract type, one struct and one `@contract` block.

**Spec coverage for this milestone.** R8 (Tasks 3-9), the `AbstractQRep` half of R9 (Task 6), the
`GivensQ` clause of R10 — `@test_typestable` plus a bounded allocation assertion, per spec
section 7 (Task 6), R11 for the routines added here (Tasks 3-10), R15 (Tasks 3, 5, 11). R12's Q
representations page is Task 11. R13's benchmark comparisons against prior art stay in M4;
`bench/` gains only the decision sweep and the compaction sweep here.

**The milestone is the conversion, not the type.** `GivensQ` is Tasks 3 to 6 and is close to the
verified prototype. Tasks 7 and 8 are the larger half: M2b's constructor, `getproperty`,
`_grow!`, `ldiv!`, `lowrankupdate!`, `insert_column!`, `delete_column!`, `shift_columns!` and the
`UpdatableQR` invariants all assume explicit storage, and each has to be rewritten against the
widened contract before a second representation can reach any of them. Ruling 1 records that this
is what M3 is.

**The contract grew from five clauses to eleven.** M2b's five are what a representation must
answer to be printed and rotated; they are not what the verbs call. The seven added here are
exactly the operations the four supported verbs and `ldiv!` invoke polymorphically, no more:
`_active`, `_augmented`, `_spare` and `_clearspare!` stay `DenseQ`-private, and `_apply!` is
defined for both representations but is not a clause because no verb calls it through the
abstract type. If a third representation ever arrives, the clause list is the checklist.

**Decided against automatic compaction.** The representation is a type parameter of
`UpdatableQR`, so a `!`-verb cannot swap it. `materialize` therefore returns a new factorization
and `compaction_due` reports when to call it, which keeps every verb's return value its own
argument. The alternative — a representation that holds either a rotation log or a dense factor
behind a runtime flag — is the union the ledger removed from `UpdatableCholesky` after measuring
its cost, and it would come back here as a two-member union on the hottest path in the package.

**Row verbs and left rotations are refused, and that is the design.** Supporting `insert_row!`
would need a stored row permutation and an identity-extended base; supporting `delete_row!` would
need the factor's rows individually, which an implicit product cannot give; `lmul!` records a
left multiplication the log has no room for. Half a pair is worth less than a clear message, so
all three throw and name `materialize`. They are the contract's optional group rather than
mandatory clauses satisfied by a throw, so the contract still says something true.

**`_augment!` checks its own precondition.** The routine's contract is `q * beta == r`, and it
holds only for an `r` orthogonal to the existing columns. A residual with a range component
returns a `beta` that misses `r` by that fraction while `norm(M' * M - I)` stays at 4.4e-16, so
every orthogonality and reconstruction check in the suite passes on a wrong answer — the same
shape as the `_lq!` diagonal-sign defect the M0/M2a ledger records. The guard is relative and has
its own test, alongside a test that the exact-zero case is not the only thing it catches.

**The out-of-block rotation is pinned against the full product.** A rotation past column `n`
leaves the thin factor orthonormal whatever plane it was recorded in, so an orthonormality
assertion constrains nothing there. Task 4 asserts against the `m x m` product the log actually
acts on. Measured: with the plane recorded one off for rotations past `n`, an orthonormality-only
item passes for both `Float64` and `ComplexF64`.

**The compaction default is a floor, not a fit.** The crossover is proportional to `m`, so one
integer cannot be right at every shape in the sweep; the constant is the smallest measured value
and both the docstring and the docs page say so. A test reads it back out of the saved samples,
so the constant and the measurement cannot drift apart silently. The sweep pushes contiguous
planes, which is what a retriangularization emits, rather than uniformly random ones.

**Known cost, stated rather than hidden.** Applying a `GivensQ` is slower than applying a
`DenseQ` from the first application, not only once the log is long: the base factor is applied
through its reflectors rather than as a matrix-vector product. `GivensQ`'s advantage is the
formation cost it never pays, which is about 1.5x `geqrf`. The Q representations page says this
plainly, and the compaction threshold is measured against the base's own cost rather than against
a dense product, because the comparison a caller faces is "keep the log or convert", not "log or
never have used this representation".

**Bounded allocation, not zero.** `_apply!` and `_applyadj!` allocate one small array per call
for the implicit base factor's own workspace — measured at 64 bytes at `(m, n) = (12, 5)`, not a
per-`m` workspace — and `rmul!` grows the log with `push!`. Task 6 asserts type stability plus a
128-byte bound rather than `@allocated == 0`, which is what catches a regression that would size
a workspace per `m`.
